# 零基础日常工作与项目规则

基础页面向没有 Git 基础的美术等成员。目前只支持已经准备好的项目文件夹，不提供下载项目。选择并保存项目根目录后自动只读检查，默认进入日常工作。

## 三个日常操作

- **更新项目**：确认后获取团队版本，只允许安全快进。先在隔离副本预检本地修改是否能取回；无冲突时备份本地修改、快进更新，再恢复原暂存状态和新增文件，保留安全备份。有冲突、历史分叉或子模块版本变化时提前停止，本地文件保持原样。
- **查看我的改动**：文件显示“新增、修改、删除、改名、需要协助”，不要求理解暂存区。清单提供“全选 / 全不选”和已选数量，批量勾选不会立即提交或更改文件；单次最多200个文件，超过时请分批选择。清单是本机项目中的改动，不能自动判断归属；只选择自己本次要提交的文件。
- **提交我的修改**：勾选文件、写一句话、核对团队要求并确认。工具新建独立工作分支，只添加所选文件，按已识别的标题/DCO要求提交，运行原生 hooks、上传，再创建团队审核请求。不会直接提交到受保护主分支，也不会自动合并。项目 hook 可能按其规则生成版本等配套文件，应由项目自身检查保证范围。

有一份 PR 模板时保留其原文、不替人勾选清单，创建送审草稿并提示负责人完善；草稿不代表已经正式送审、通过审核或合入。模板有多个候选时停止，让负责人确定。已有暂存内容、工作分支上有未进入团队正式版本的记录时停止，避免夹带旧修改。

已有项目应由负责人配置好 Git 身份、origin、原生检查、LFS（项目需要时）以及已连接的 gh 审核账号。缺组件、账号、权限或配置时给出中文处理提示，不要求美术输入命令或密钥。

## 项目规则始终有效

工具保护 main、master 和本地 origin/HEAD 所指默认分支，禁止专业入口直接提交和推送；日常提交先自动新建工作分支，再通过 PR 审核。不是实时远端保护查询；远端额外策略仍由服务器执行。

有界读取根 AGENTS.md、CONTRIBUTING.md、跟踪的嵌套 AGENTS、项目内 Markdown 引用和 PR 模板。最多80份候选、单份128KB、正文总量1 MiB；不读外部链接或符号链接目标，未完整读取时阻塞。提交确认页可展开本项目要求原文，拿不准先联系负责人，不把程序员术语放在主要操作上。

检查实际 core.hooksPath 和可执行性；项目有 .githooks 但未启用，或 hook 不可执行时阻塞。保留原生 hooks、LFS检查、提交签名配置和服务端规则；不提供强推、重置、清理、跳过 hooks 或假验收；仅更新项目在预检通过后自动备份与取回修改。识别 DCO 时附加 signoff，识别 Conventional Commits 时为一句话加 chore 前缀，更严格格式仍由项目原生检查执行。

任意自然语言项目规则不能由通用 Git 工具完全自动验证。未被 hooks 覆盖的测试、审批、资源锁定和业务条件必须实际完成，确认项仅记录人工确认，不能代替执行。无法判断时请负责人核对；发现了规则文件不等于“全部规则自动通过”。高级工作流同样必须遵守这些要求。

## 更新进度

确认更新后显示当前阶段、已完成步骤和已用时间。阶段来自当前操作的真实持久记录，包含获取团队版本、冲突预检、备份本地修改、更新文件、取回修改；没有本地修改时自动跳过备份和取回。无法取得字节下载百分比时显示不定进度动画，不按时间伪造百分比。只有更新请求确认成功才显示完成；查询进度失败不重试更新、不解除操作锁，错误结果停止动画并提示核对。进度查询只在当前更新期间运行，不是后台定时任务。

## 结果与恢复

每次写入使用十分钟内的一次性票据，绑定根目录、分支、HEAD、暂存内容、工作区状态、规则与 hook 摘要，执行前重查。同仓进程内串行，另用 Git 元数据中的 jixin-write.lock 排除桌面和插件同时写入；异常退出留下锁时由负责人核对实际状态后处理，不自动删除锁或重放写入。

复合操作副作用前在 Git 元数据 jixin-beginner.json 原子记录步骤，不写进项目工作树。当前操作编号重复请求只返回原回执，不重发提交、上传或送审。中断、hook拒绝、上传/送审结果不明会持久阻塞，并区分“本地保存”“已上传”“草稿待完善”“等待审核”；重新打开仍可核对。更多工具里的明确确认只允许后续新操作，不会重放旧操作。历史记录不是完整审计日志，负责人仍须核对实际仓库及远端。

## 高级入口与验证范围

Cindy 的高级界面保留五工作流和折叠专业 Git 工具；独立桌面保留折叠“更多工具（项目负责人）”。专业工具包括差异、历史、分支、暂存、提交、获取、快进拉取、推送、填写 PR 模板。独立端高级 AI 工作流和 AI 问题诊断尚未实现。

真实临时仓库和本地 bare 远端验证自动分支、所选文件、DCO、hooks、快进、分叉阻止和故障回执；gh 使用替身验证参数，不创建真实外部 PR。真实 Electron 和最终打包二进制验证日常三步操作、取消、持久回执；模拟 Cindy 验证 RPC、原高级流程、零 AI 派发及320/860px明暗和英文。业务项目写入、真实远端 PR 和真实 Cindy 安装不包含在这些证据中。

## 对应自己的 GitHub Issue

提交页可按需点“加载我的事项”，默认列出当前项目中“分配给我的”未关闭 Issue，也可切换“我创建的”。页面显示实际仓库、当前GitHub账号和事项编号/标题；每次最多100项，未命中可切换范围或请负责人协助。列表不会后台自动联网，读取失败不自动重试；不关联时不增加这次网络读取。账号沿用本机gh，不要求成员输入命令或凭证。

项目origin必须是GitHub.com的HTTPS/SSH地址；当前不支持GitHub Enterprise、自定义SSH别名或其它代码托管平台的Issue列表。所有读取明确绑定origin仓库，忽略GH_REPO/GH_HOST对仓库选择的覆盖，不扫描其它项目。

选中后提交前重新查询：Issue仍开放、属于同一仓库、且分配给当前账号或由其创建，才继续新建工作分支；失败不暂存或提交文件。用户只传编号和仓库，标题/链接由服务端重读，不能用页面伪造跨库链接。仓库或账号变化后须重新选择适用事项。

提交记录附加Refs链接，送审描述附加关联事项完整链接，持久回执保留编号、标题与链接。工具不自动关闭Issue、不修改负责人/标签、不自动勾验收；项目要求的Issue格式、审批与原生hooks仍适用。取消关联不代表满足项目的强制关联要求，严格约定仍由原生门禁和人工核对执行。
